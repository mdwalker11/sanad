# سند (Sanad) — العرض الكامل المبدئي وخطة التنفيذ 0.1

## 1. ملخص المشروع

سند تطبيق موحد للعميل والعامل/العاملة على Android وiOS، مع لوحة تشغيل إدارية على الويب، يبدأ في طرابلس ويقدم خدمات منزلية موثوقة.

### الخدمات الأولى

- تنظيف المنازل — عاملات نسائية.
- التكييف والتبريد.
- السباكة.
- الكهرباء.
- فك وتركيب الأثاث ضمن نطاق محدود.

### نموذج العمل

العامل يرسل عرض السعر، والعميل يختار العرض. فريق سند يدير التحقق والمطابقة والجودة والشكاوى والتشغيل.

## 3. المعمارية المقترحة

```text
Flutter mobile app
  ├── customer role
  ├── worker role
  └── shared components

Admin dashboard

Backend API + Auth
  ├── PostgreSQL
  ├── Object storage
  ├── Push notifications
  ├── SMS provider
  ├── Maps provider
  └── Payment provider later
```

### قرارات مهمة

- التطبيق الموحد لا يعني صلاحيات موحدة؛ Backend يفرض الدور والصلاحية.
- نبدأ بالدفع النقدي، ثم نضيف بوابة دفع ليبية مرخصة بعد التحقق.
- نبدأ بتشغيل مُدار ومطابقة تحت إشراف سند.
- الذكاء الاصطناعي يساعد في التصنيف والتلخيص والتقارير، ولا يتخذ قرارات السلامة أو التعويض أو السعر النهائي وحده.
- نستخدم Modular Flutter حتى يمكن فصل تطبيق العامل مستقبلًا إذا أثبتت البيانات الحاجة.

## 4. مراحل التنفيذ

المخرجات:

- PRD 0.2.
- تحديد المناطق الأولى في طرابلس.
- سياسة الأسعار والعروض.
- سياسة العمولة والإلغاء.

بوابة الانتقال: لا يبدأ البناء الإنتاجي قبل اعتماد القواعد التي تؤثر في قاعدة البيانات وتجربة الحجز.

### المرحلة 2 — الأساس التقني

## 5. ما نحتاجه من المالك

### قرارات المنتج

1. مناطق طرابلس الأولى.
2. هل يختار العميل موعدًا محددًا أم نطاقًا زمنيًا؟
3. نسبة العمولة أو رسم المنصة.
4. رسوم الزيارة والمعاينة.
5. سياسة الإلغاء.
6. سياسة الضمان وإعادة الزيارة.
7. الحد الأقصى للتكلفة الإضافية دون مراجعة تشغيلية.
8. قواعد التنظيف النسائي والخصوصية.
9. هل يمكن للعامل قبول طلبات من أي جنس أم حسب قواعد الخدمة؟
10. ساعات التشغيل والطوارئ.

### المحتوى والهوية

- الشعار أو الموافقة على تصميمه.
- ألوان وهوية سند إن وجدت.
- الاسم القانوني للشركة.
- رقم خدمة العملاء.
- البريد الرسمي.
- وصف الخدمات والأسعار الإرشادية.
- نصوص سياسة الخصوصية وشروط الاستخدام بعد مراجعتها قانونيًا.
- صور الخدمات أو موافقة استخدام صور مرخصة.

### الشبكة التشغيلية

نحتاج ملفًا منظمًا للعاملين السابقين، دون إرسال كلمات مرور، يحتوي إن أمكن على:

- الاسم.
- الهاتف.
- التخصص.
- المنطقة.
- سنوات الخبرة.
- توفره.
- هل لديه أدوات ومواصلات؟
- هل يوافق على التحقق والعمولة؟
- حالة التواصل.

يجب أن يكون للمالك الحق القانوني في مشاركة هذه البيانات مع فريق التطوير، وأن يتم التعامل معها بسرية.

### الحسابات المملوكة للمالك

ينشئها المالك باسمه أو باسم الشركة:

- GitHub/GitLab.
- Google Play Console.
- Apple Developer Program.
- Apple App Store Connect.
- Firebase أو Supabase.
- مزود SMS.
- مزود الخرائط.
- مزود التخزين والمراقبة.
- مزود الدفع الليبي عند اعتماده.
- نطاق الموقع والبريد الرسمي.

الحسابات يجب أن تبقى ملكًا للمالك، ولا تُنشأ على حساب مطور شخصي.

## 6. المتطلبات الخاصة بـ iOS

- حساب Apple Developer باسم المالك أو الشركة.
- جهاز Mac أو خدمة CI/CD macOS للبناء والتوقيع.
- Bundle ID.
- شهادات التوقيع وإعدادات provisioning.
- App Store Connect.
- TestFlight.

لا يمكن رفع iOS إلى App Store دون حساب Apple Developer وبيئة macOS/Xcode أو خدمة بناء macOS موثوقة.

## 7. ما لا نحتاجه الآن

- كلمات المرور داخل المحادثة.
- مفاتيح البطاقات.
- مفاتيح الإنتاج.
- شهادات Apple الخاصة.
- ملف توقيع Android الخاص.
- فتح صلاحية كاملة للجهاز.
- دفع إلكتروني قبل اختيار مزود مرخص.
- جميع الـ200 عامل دفعة واحدة.

الأسرار تدخل في مدير أسرار أو متغيرات بيئة آمنة، وتبقى خارج Git.

## 8. طريقة العمل وضمان الجودة

- كل مهمة لها Issue.
- كل ميزة تعمل في Branch.
- كتابة الاختبار قبل كود الإنتاج للوظائف الجديدة.
- تشغيل lint وtests وbuild قبل الدمج.
- مراجعة مستقلة للكود.
- لا يوجد ادعاء بأن ميزة جاهزة دون مخرجات تشغيل حقيقية.
- لا يتم نشر الإنتاج من دون مراجعة المالك.
- لا يتم تغيير مخطط قاعدة البيانات دون migration موثقة.

## 9. معايير القبول للإصدار الأول

يعتبر MVP جاهزًا فقط عندما:

- يستطيع عميل جديد التسجيل وإنشاء طلب حقيقي.
- يستطيع التشغيل رؤية الطلب وإرساله للعاملين.
- يستطيع عامل موثق إرسال عرض.
- يستطيع العميل مقارنة العرض وقبوله.
- يستطيع العامل تحديث حالة المهمة.
- يستطيع العميل تأكيد الإنجاز والتقييم.
- يستطيع التشغيل فتح شكوى ومعالجتها.
- تمنع الصلاحيات الوصول غير المصرح.
- تعمل المسارات الأساسية على Android وiOS.
- توجد اختبارات للمسارات الحرجة.
- يمكن إصدار نسخة staging قابلة للاختبار.
- توجد نسخ احتياطية وسجلات أخطاء.
- توجد وثائق تسليم وتشغيل.

## 10. وضع المشروع الحالي

الموجود حاليًا في مساحة العمل:

- `docs/PRD-0.1.md` — وثيقة متطلبات أولية محدثة.
- `index.html` — نموذج واجهة أولي سابق، وليس تطبيقًا إنتاجيًا.

الخطوة التالية بعد اعتماد العرض هي إنشاء هيكل المشروع الحقيقي، وليس تحويل النموذج HTML مباشرة إلى منتج نهائي.

## 11. حدود الوعد

سنقوم بإنشاء الكود والملفات والبنية والاختبارات وتجهيزات البناء داخل مستودع المشروع، ونجهز ملفات الإصدار. أما الحسابات المدفوعة، التحقق القانوني، الاعتماد التجاري، قبول المتاجر، وتوفر الأجهزة والحسابات فهي تعتمد على المالك وقرارات الجهات الخارجية.

لا يمكن ضمان قبول App Store أو Google Play أو الانتشار التجاري، لكن يمكن تجهيز المنتج وفق المتطلبات، اختباره، وتحسين فرص القبول والنجاح.
