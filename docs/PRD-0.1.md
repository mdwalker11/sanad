# سند (Sanad) — وثيقة متطلبات المنتج PRD 0.1

**الحالة:** مسودة اعتماد أولية
**النطاق الجغرافي:** طرابلس، ليبيا
**المنصات:** تطبيق سند موحد Android/iOS بأدوار عميل وعامل، ولوحة تشغيل إدارية Web
**اللغة الأساسية:** العربية RTL
**اللغة المستقبلية:** الإنجليزية

## 1. الرؤية

سند منصة موثوقة لإدارة وحجز الخدمات المنزلية في طرابلس. لا تكتفي المنصة بربط العميل بالفني، بل تتحكم في التحقق، المطابقة، متابعة التنفيذ، الدفع، التقييم، والشكاوى.

الرسالة التسويقية الأولية:

> اطلب فنيًا موثوقًا إلى منزلك، بسعر واضح وموعد محدد.

## 2. قرارات المؤسس المعتمدة

- البداية من طرابلس فقط، ثم التوسع إلى مدن ودول أخرى بعد إثبات النموذج.
- الجمهور يشمل العملاء الأفراد والشركات.
- لا توجد شبكة حالية، لكن توجد خبرة سابقة في استقطاب نحو 200 عامل مسجل؛ نستخدم ذلك كقناة أولية لبناء شبكة العاملين.
- العامل/الفني يرسل عرض السعر للخدمة من خلال المنصة.
- فريق سند يدير التشغيل والمطابقة والجودة والشكاوى في المرحلة الأولى.
- الاسم: سند — Sanad.
- خدمات التنظيف في الإصدار الأول تقدمها عاملات نسائية فقط، مع مطابقة مناسبة للخصوصية والجغرافيا.

## 3. نطاق MVP

### الخدمات عند الإطلاق

1. تنظيف المنازل — عاملات نسائية.
2. التكييف والتبريد.
3. السباكة.
4. الكهرباء.
5. فك وتركيب الأثاث ضمن نطاق محدود.

### خارج النطاق الأولي

- الدهانات الكاملة.
- أعمال البناء والنجارة الكبيرة.
- نقل الأثاث الكامل.
- مكافحة الحشرات.
- الحدائق والمسابح.
- رعاية الأطفال أو كبار السن.
- أي خدمة عالية الخطورة أو غير قابلة للضبط قبل وضع سياسة تشغيل وتأمين مناسبة.

## 4. نموذج التشغيل

سند تبدأ كسوق خدمات مُدار، وليس سوقًا مفتوحًا بالكامل:

1. يسجل العامل ويرفع بياناته ووثائقه وتخصصاته ومناطق عمله.
2. يراجع فريق التشغيل الحساب يدويًا.
3. ينشئ العميل طلبًا بوصف وصور وموعد وموقع.
4. يراجع النظام أو فريق التشغيل الطلب.
5. يرسل الطلب إلى عاملين مؤهلين ضمن المنطقة والتخصص والتوفر.
6. يرسل العامل عرضًا منظمًا يتضمن السعر، زمن الوصول، مدة التنفيذ، وما يشمله السعر.
7. يختار العميل العرض أو يساعده فريق التشغيل.
8. يبدأ العمل بعد تأكيد المهمة وكود بدء الخدمة.
9. يرفع العامل صور قبل/بعد عند الحاجة، ثم يطلب إغلاق المهمة.
10. يؤكد العميل الإنجاز، ثم يتم الدفع والتقييم.
11. تتعامل سند مع الشكاوى والضمان وفق سياسة واضحة.

## 5. نموذج التسعير المعتمد

العامل يضع السعر، لكن ليس بشكل حر وغير منظم. كل عرض يجب أن يحتوي على:

- سعر الزيارة أو المعاينة إن وجد.
- سعر العمالة.
- المواد أو القطع، إن وجدت.
- مدة صلاحية العرض.
- وقت الوصول المتوقع.
- مدة التنفيذ المتوقعة.
- ما يشمله السعر وما لا يشمله.
- سياسة الضمان.

تضع سند لاحقًا نطاقات إرشادية لكل خدمة ومنطقة لمنع الأسعار غير الواقعية، وتحتفظ بحق طلب مراجعة أو رفض عرض غير منطقي.

لا يسمح بإضافة تكلفة خارج العرض إلا بعد موافقة العميل داخل التطبيق.

## 6. أنواع المستخدمين

### العميل الفرد

يطلب خدمة لمنزل أو عقار شخصي.

### عميل الشركة

يحجز خدمات لمكتب أو عقار أو عدة مواقع، ويحتاج لاحقًا إلى:

- بيانات شركة.
- فواتير وتقارير.
- عدة عناوين.
- مستخدمين وصلاحيات.
- سجل خدمات شهري.

في MVP يدعم النظام حساب الشركة الأساسي دون بناء نظام مؤسسي كامل.

### العاملة/الفني

يقدم خدمة بعد التحقق والموافقة.

### المشرف/موظف التشغيل

يدير المطابقة، الطلبات، الإلغاء، الشكاوى، والعروض.

### المدير

يدير الصلاحيات والخدمات والأسعار والتقارير والإعدادات.

## 7. تطبيق سند الموحد

يستخدم العميل والعامل التطبيق نفسه، لكن كل مستخدم يرى واجهة وصلاحيات مختلفة بعد تسجيل الدخول حسب الدور. هذا يقلل تكلفة التطوير والنشر ويحافظ على تجربة موحدة، مع إمكانية فصل التطبيقين لاحقًا إذا أثبتت البيانات أن ذلك ضروري.

### اختيار الدور

- عميل: طلب ومتابعة الخدمات.
- عامل/عاملة: استقبال الطلبات وإرسال العروض وتنفيذها.
- يمكن للحساب أن يطلب تفعيل دور العامل بعد مراجعة الوثائق؛ لا يتحول العميل إلى عامل تلقائيًا.
- لا تظهر بيانات أو شاشات الدور الآخر دون صلاحية.

### شاشات العميل الأساسية

- الترحيب وتحديد اللغة.
- تسجيل الدخول برقم الهاتف.
- الصفحة الرئيسية.
- فئات الخدمات.
- تفاصيل الخدمة.
- إنشاء طلب.
- رفع الصور/الفيديو.
- تحديد العنوان والموقع.
- تحديد الموعد والمرونة الزمنية.
- مقارنة عروض العاملين.
- تفاصيل العرض.
- حالة الطلب وتتبع المراحل.
- التواصل المنضبط مع سند/العامل.
- تأكيد اكتمال الخدمة.
- الدفع.
- التقييم.
- الشكوى والضمان.
- سجل الطلبات.
- الحساب والعناوين والإشعارات.

### متطلبات سهولة الاستخدام

- إنشاء الطلب الأساسي خلال أقل عدد ممكن من الخطوات.
- لغة عربية واضحة وغير تقنية.
- دعم العنوان النصي مع الموقع؛ لا نعتمد على GPS وحده.
- العمل بشكل مقبول مع اتصال ضعيف.
- إظهار السعر والموعد وما يشمله العرض قبل التأكيد.
- دعم مشاركة الطلب أو دعوة صديق لاحقًا.

## 11. الثقة والسلامة

- تحقق من رقم الهاتف والهوية.
- مراجعة يدوية للعامل.
- اختبار مهني أو مقابلة حسب الفئة.
- صورة وملف مهني واضح.
- تقييم لا يفتح إلا بعد طلب مكتمل.
- كود بدء الخدمة.
- صور قبل/بعد للخدمات المؤهلة.
- سجل محادثة داخل النظام.
- منع الدفع خارج العرض المسجل قدر الإمكان.
- سياسة إلغاء واضحة.
- سياسة ضمان حسب نوع الخدمة.
- تصعيد بشري للحالات الحساسة.
- لا يقدم الذكاء الاصطناعي تشخيصًا نهائيًا للكهرباء أو الغاز أو الأعطال الخطرة.

## 12. الدفع

## 18. قرار معماري: تطبيق موحد حاليًا

نبدأ بتطبيق واحد باسم سند يضم دور العميل ودور العامل، مع تطبيق لوحة الإدارة على الويب. هذا القرار مناسب للمرحلة الأولى لأن حجم الفريق والميزانية وسرعة اختبار السوق أهم من الفصل المبكر.

### المزايا

- قاعدة كود وملف متجر واحدان.
- تحديثات أسرع.
- تكلفة أقل.
- مشاركة مكونات التصميم والمصادقة والإشعارات.
- سهولة إضافة حساب يسمح للمستخدم بالعمل كعميل وعامل بعد التحقق.

### الضوابط

- فصل صارم للصلاحيات على مستوى Backend، وليس الواجهة فقط.
- كل Endpoint يتحقق من الدور والصلاحية.
- لا نعتمد على إخفاء زر أو شاشة كحماية.
- تفعيل دور العامل يحتاج موافقة الإدارة.
- اختبارات منفصلة لمسارات العميل والعامل.
- تصميم بنية Flutter إلى وحدات `customer` و`worker` و`shared` حتى يمكن فصل التطبيقات لاحقًا دون إعادة كتابة النظام.

### متى نفصل التطبيقين؟

نراجع القرار بعد توفر بيانات الاستخدام. قد نفصل التطبيقين لاحقًا إذا:

- أصبحت واجهة العامل كبيرة ومختلفة جذريًا.
- احتاج العامل إلى تشغيل مستمر وإشعارات كثيفة.
- زادت مشاكل الأداء أو حجم التطبيق.
- أصبح لكل دور دورة إصدار مختلفة.
- أظهرت تحليلات المتاجر أن الفصل يحسن التحويل أو الاحتفاظ.

لا نفصل الآن لمجرد التوقع؛ نبدأ موحدين ونترك الباب مفتوحًا.
